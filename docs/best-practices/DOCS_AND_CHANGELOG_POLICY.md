# Политика документации и CHANGELOG

## Что обязательно обновлять

При **любом** изменении в кодовой базе:

1. **`CHANGELOG.md`** — всегда.
2. **`README.md`** — если изменился публичный API, структура проекта или команды.
3. **`docs/`** — если изменились конфигурация, схема событий, интеграция или процессы.

## Формат CHANGELOG

Следуем [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/).

```markdown
## [X.Y.Z] — YYYY-MM-DD

### Added
- Новая функциональность.

### Changed
- Изменения в существующей функциональности.

### Deprecated
- Функциональность, которая будет удалена.

### Removed
- Удалённая функциональность.

### Fixed
- Исправления багов.

### Security
- Исправления уязвимостей.
```

### Правила

- Каждая запись — одно предложение, начинающееся с глагола.
- Указывать затронутый модуль, если неочевидно: `[rdr]`, `[extensions]`, `[docs]`.
- Не объединять несвязанные изменения в одну запись.

## Структура docs/

```
docs/
  rdr/                        # документация модуля RDR
    CONFIG.md                 # справочник конфигурации RDR
    EVENT_SCHEMA.md           # схема LogEntry
    INTEGRATION.md            # руководство по интеграции RDR
  rt/                         # документация модуля RT
    CONFIG.md                 # справочник конфигурации RT
    EVENT_SCHEMA.md           # схема RTLogEntry
    INTEGRATION.md            # руководство по интеграции RT
  checklists/
    UPDATE_CHECKLIST.md       # после каждого обновления
    RELEASE_CHECKLIST.md      # процесс релиза в npm
  best-practices/
    SEMVER_POLICY.md          # когда patch/minor/major
    TESTING_POLICY.md         # правила работы с тестами
    DOCS_AND_CHANGELOG_POLICY.md  # этот документ
  agent/
    HOW_TO_GIVE_TASKS.md      # как давать задачи модели
    UPDATE_KNOWLEDGE_PROTOCOL.md  # протокол обновления документации
```

Каждый модуль (`rdr`, `rt`, будущие) имеет **свою** директорию в `docs/`.

## README.md

README должен содержать:
- Краткое описание библиотеки.
- Установку и Quick Start.
- Описание публичного API.
- Ссылки на детальные docs.
- Описание структуры проекта.
- Доступные команды тестов.
